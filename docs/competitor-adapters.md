# Competitor adapters

All nine existing competitor fixtures use Next.js 16.0.7, React 19.2.1, the shared article and page interaction, and a `/baseline` route without a CMP. The canonical v3 configuration is `benchmarks/with-<vendor>/run.json`. Historical v1 configuration files have been removed from these fixtures.

The public integration IDs already present in this repository remain in use. OneTrust uses the existing same-ID test publication with the `-test` suffix. No vendor accounts or hosted configurations were created or edited. Each CMP loads its actual remote SDK. The local bridge reads public SDK permission state, distinguishes effective permissions from an explicit choice, and inserts the controlled measurement or marketing script only when that permission is true. This tests callback integration. The historical `3.0.0-next-client-effect` fixtures start SDK scripts after Next hydration. The current article workload starts Cookie Control at the end of body, Didomi, Enzuzo, and OneTrust at the opening head, and iubenda at the end of head. These five placements use the same public callbacks and async SDK insertion, with a fixture-proxy bootstrap. Ketch and Osano retain client-effect startup because their retrieved documentation did not establish the supported embed placement. [The fixture audit](audit-fixture-realism.md) records exact sources, new revisions, serving policy, and limits. Historical measurements keep their original topology and are not relabeled as results of the changed fixtures. Osano additionally applies its native blocker; controlled script nodes carry its public category annotations before SDK interception begins. The page's Privacy preferences button invokes the vendor's public preferences API; it does not supply a replacement consent interface.

The first browser inventory is functional reconnaissance, not a performance result. Raw evidence is in [initial-browser-probe.json](evidence/competitors/initial-browser-probe.json). The separate [HTTP probe](evidence/competitors/initial-http-probe.json) records that direct HTTP clients received 403 for CookieYes and OneTrust while Chromium received their scripts. A 403 from that probe does not establish that the browser integration is unavailable.

## Protocol and provenance

Every configuration declares load, accept, reject, preferences, granular save, withdrawal, returning acceptance/rejection, keyboard rejection, and a separate 100 ms followup diagnostic. Ordinary followups use 500 ms. Unsupported or blocked flows remain in the matrix with their failure evidence. They are not converted into successful zero-duration measurements.

The remote SDKs and policy documents can change at their existing URLs. Preflight content digests identify the bytes inspected on that date; they do not establish an immutable release or prove that a later browser received the same bytes. Candidate fixtures use `artifactPolicy: "mutable-network"`. Measured response digests and drift checks are recorded by the runner. Do not interpret `remote-capture-*` labels as vendor release versions. Cookie Control's explicit 9.10.1 URL still requires its captured content digest.

Ketch's preparation clicks and final Save click remain separate in raw evidence. Cookie Control's immediate granular changes use a separate functional probe before any transactional save comparison is meaningful. A missing native Save control is a protocol coverage limit, not evidence that the product lacks granular consent.
